# T3 Code versus Tabs: non-mobile feature gap report

Reviewed on **6 October 2026 (India time)**.

## Conclusion

Tabs already implements a substantial part of T3 Code's earlier feature set and adds its own integrated Code-OSS workspace, browser tools, testing workflows, and additional provider integrations. The remaining differences are concentrated in **agent orchestration, unattended work, provider flexibility, and remote/server operations**.

The most valuable gaps to consider are:

1. Durable delegation and agent access to other threads.
2. Scheduled follow-ups and webhook-triggered work.
3. Switching providers within an existing conversation, with context carried across.
4. Thread forks and worktree handoff with preserved conversation history.
5. Automatic continuation after a provider usage limit resets.
6. Generic ACP agent installation and managed ChatGPT account connections.

These are source-level findings, not results from interactive testing. “Present” means an implementation was found; it does not certify that every path works in a packaged release. No product features were ported or removed during this review.

## How to read the findings

- **Missing:** no corresponding first-class implementation was found in Tabs' active source, contracts, and relevant entry points.
- **Partial:** Tabs has part of the capability, but the specific upstream workflow is absent or narrower.
- **Architecture gap:** upstream has a different supporting implementation. This is a design decision to evaluate, not a demand to copy its architecture wholesale.
- **Compatibility review:** a corresponding integration exists, but this review does not establish parity with the latest upstream protocol.

The areas below overlap. For example, delegation and scheduled work share orchestration infrastructure. They should not be treated as an additive estimate of implementation effort.

## Suggested decision order

This is a proposed backlog, not authorization to implement it.

| Order | Work to assess                                                                         | Why                                                                                                             |
| ----- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 1     | Thread-reading/tools plus portable context transfer and provider switching             | Removes the existing provider lock and supplies the foundation for coordinated agent work                       |
| 2     | Durable task delegation and subagent lifecycle                                         | Enables parallel work across providers with tracked results, approval routing, and cancellation                 |
| 3     | Scheduled follow-ups and limit-reset continuation                                      | Adds unattended work that survives UI closure and server restart                                                |
| 4     | Thread forks/worktree handoff, then webhook tasks                                      | Builds on durable conversation/run state; webhook delivery also depends on network exposure                     |
| 5     | Generic ACP onboarding, Pi, and managed ChatGPT connection assessment                  | Expands provider choice and reduces setup friction; these are separate integrations with different requirements |
| 6     | HTML replies, richer context chips, secrets, storage policy, and remote balancing      | Adds focused workflow improvements after the required runtime contracts are clear                               |
| 7     | Forgejo/Gitea, WSL management, expanded CLI lifecycle, and PR progress/watch additions | Prioritize according to actual user demand and deployment needs                                                 |

T3's V2 runtime is a reference for the first four items. A safe design assessment should map its state transitions and persisted records onto Tabs before deciding between selective ports and a coordinated runtime migration. Copying upstream services individually without their persistence, request, and recovery contracts would leave incomplete behavior.

## Optional desktop capabilities and remaining verification

This is distinct from the T3 mobile app, but is mobile-development tooling. It is left out of the recommended backlog because mobile work is not currently needed.

- **OpenCode 2, ACP v2 details, Codex async questions/app approvals:** protocol compatibility needs focused integration tests with the installed provider versions. Generated protocol definitions alone are insufficient evidence of an exposed working feature.
- **Packaged execution:** this review did not launch either application, change credentials, connect remote servers, or run provider-backed tasks. It did not run product build/typecheck/test suites because no product source was changed. Source presence and upstream tests were inspected as evidence, without claiming those tests passed here.

The report is a broad feature/workflow inventory with concrete source references, not an exhaustive proof that every upstream behavior is absent or present. A later implementation pass should turn each selected gap into explicit acceptance criteria and test the complete UI-to-server-to-provider path.
